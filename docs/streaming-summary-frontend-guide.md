# 前端联动指南：Agent 总结流式渲染（summary_delta）

## 背景

Agent 流程（`sql_query` / `workflow` / `db_compare`）的最后一步总结，此前是后端一次阻塞式全量调用：
生成期间前端只能停留在 `thinking`（"正在生成总结..."）状态，生成完成后通过单个 `summary`
事件一次性下发整篇 Markdown。总结携带全量上下文，耗时常常十几秒到几十秒，导致：

1. 总结阶段长时间无任何事件，用户误以为连接卡死；
2. 总结内容"整段蹦出"，没有与简单会话 `content` 一致的打字机效果。

后端现已改为**流式聚合**：总结生成过程中实时下发 `summary_delta` 增量事件（总结的思考过程
同样以 `reasoning` 增量下发），流结束后仍下发一条 `summary` 全量事件用于终态定稿与落库。
本文说明前端需要的配套改动与最终效果。

## 接口变更

最新协议以仓库根目录 `README.md` 的 "SSE Event Protocol" 章节与 `api-docs.yaml`
（`/chat` 端点说明、`SseEvent` schema）为准。事件外层结构不变：

```json
{
  "taskId": "uuid",
  "step": 2,
  "type": "summary_delta",
  "content": "## 查询结果\n\n",
  "timestamp": 1719648004500
}
```

变更点：

| 事件 | 语义 |
|------|------|
| `summary_delta`（**新增**） | 最终总结的流式 Markdown 增量片段，连续多条，按到达顺序拼接即总结全文 |
| `summary`（语义明确） | 终态全量 Markdown 总结，**权威内容**：前端应以其覆盖流式增量完成最终渲染 |
| `reasoning`（不变） | 总结阶段若模型处于 thinking 模式，会先下发思考增量，复用现有 reasoning 渲染即可 |

总结阶段的事件顺序：

```
thinking   "正在生成总结..."
reasoning*           （可选，总结的思考增量）
summary_delta*       （Markdown 增量，打字机渲染）
summary              （全量定稿，覆盖渲染）
usage
done
```

`step` 字段携带最后一个 Agent 步骤的序号，与既有 `summary` 事件一致。

## 前端改动点

1. 事件分发新增 `summary_delta` 分支：将 `content` 追加到总结卡片缓冲区并增量渲染。
   由于 Markdown 片段在拼接过程中可能临时不完整（如表格行只到一半），建议每次收到增量后
   用"已拼接全文"整体重渲染，而不是逐片段独立渲染。
2. `summary` 事件到达时，用其全量内容**覆盖**总结卡片并定稿（正常路径下与增量拼接结果
   一致；后端降级/兜底路径下它是唯一权威内容），历史消息回显仍以此为准。
3. 总结阶段的 `reasoning` 增量复用现有"思考过程"组件渲染，无需特殊处理。
4. 兼容策略：未适配 `summary_delta` 的旧前端按未知类型忽略即可，仍由 `summary` 全量渲染，
   功能不受影响，仅失去打字机效果；新前端不要把 `summary` 再次追加渲染，避免内容重复。

## 改动后的效果

- 总结阶段不再静默：思考增量与 Markdown 正文随生成随上屏，长总结的感知等待从"整段空白"
  变为持续输出；
- 总结卡片具备与简单会话一致的打字机体验；
- 异常路径（模型报错、空回复）后端回退为简化总结，前端以终态 `summary` 全量覆盖展示，
  渲染结果始终收敛到单一权威内容，不会出现半截或重复文本。
