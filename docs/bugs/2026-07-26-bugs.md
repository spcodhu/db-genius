1. 当前的工作流和对比步骤对前端是透明的，但是不是实时的。比如“意图识别中”和“意图识别结果”是在意图识别完成之后同时返回前端的，导致用户在发起会话到接收到第一个 token 之前等待的时间过长。

---

## 2026-07-28 根因与修复结论

### 根因（三层）

1. **主因 — Agent 步骤级静默**：`ToolCallAgent.think()` 用阻塞 `.call()` 调 DeepSeek，thinking 模式下单步静默数十秒~分钟级无任何事件，完成后 `reasoning`（整块）+ `step` 事件同时爆发；`onFinish` 的 summary 生成又是一段阻塞静默。事件只能成批到达，天然“不实时”。
2. **并发放大器 — 裸用 ForkJoinPool commonPool**：`IntentRouter` 和 `BaseAgent` 的 `CompletableFuture.runAsync` 未传 executor。Agent step 循环一个任务占一个 commonPool 线程跑几分钟（阻塞在同步 HTTP，不触发 FJP 补偿），少量并发会话即可占满（pool 大小 = CPU 核数-1）→ 新请求的路由任务排队，连 `classifying` 都发不出 → 前端看到“意图识别中/结果同时到达”。
3. **残余嫌疑 — 前端/中间链路**：后端链路无缓冲点（SseEmitter 逐事件 flush，无 nginx/压缩/响应包装 Filter）。若单会话空闲时仍观察到意图事件同时到达，需排查前端流读取方式或开发代理；后端已加防御性响应头。

### 修复内容

- `ReasoningChatModel` 新增 `streamAggregated(Prompt, Consumer)`：自建请求（保留 reasoning_content 回传）走流式，reasoning 增量实时回调，tool_call 分片按 index 合并，聚合成与 `call()` 同构的响应。
- `ToolCallAgent.think()` 改用流式聚合，`reasoning` 事件从“每 step 一条整块”改为流式增量片段（与 simple_chat 一致）；`onFinish` 在 summary 生成前补发 `thinking` 状态事件。
- 新增 `ChatExecutorConfig.chatTaskExecutor`（core=8/max=32/queue=200），`IntentRouter` 与三个 Agent Handler 注入使用，替代 commonPool。
- `ChatController` SSE 响应增加 `X-Accel-Buffering: no`、`Cache-Control: no-cache` 防御头。
- 测试：`ReasoningChatModelTest` 新增流式聚合用例（增量回调 + tool_call 分片合并 + stream=true + 回传保持）；全量编译与 agent/web 模块测试通过。
- 文档：`api-docs.yaml`、README 的 `reasoning` 事件语义已更新为流式增量。

### 前端协调点

Agent 流程的 `reasoning` 事件语义变为流式增量片段，前端需按追加渲染（simple_chat 已是追加语义，可复用同一处理逻辑）。若前端此前对 Agent 的 reasoning 按 step 整块替换渲染，需要调整。
