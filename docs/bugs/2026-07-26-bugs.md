# 2026-07-26 Bug：SSE 事件"不实时"（工作流/对比步骤成批到达）

## 1. Bug 现象（原始记录）

> 当前的工作流和对比步骤对前端是透明的，但是不是实时的。比如"意图识别中"和"意图识别结果"是在意图识别完成之后同时返回前端的，导致用户在发起会话到接收到第一个 token 之前等待的时间过长。

具体表现：

- 发起 `/chat` 会话后，前端长时间没有任何反馈；
- `classifying`（意图识别中）和 `classified`（意图识别结果）两个事件在意图识别完成后**同时**到达前端；
- 工作流/对比的各步骤事件（reasoning、step 等）能收到，但不是随执行逐步到达，而是成批到达。

## 2. 排查过程

### 2.1 先排除后端"显式缓冲"的嫌疑

对后端 SSE 链路做了逐层走查：

- `ChatController` → `IntentRouter.route()` → `SseEmitter`：`classifying` 事件在 `IntentRouter.java` 中是**先于**意图分类 LLM 调用发送的，代码顺序没有问题；
- Spring `SseEmitter.send()` 每个事件都会立即 flush，不存在框架级攒批；
- 全仓库排查了可能包装响应的组件：无 nginx（当时以为）、无 `server.compression`、无任何 `OncePerRequestFilter`/`HttpServletResponseWrapper`/`ShallowEtagHeaderFilter`，`SaTokenConfig`/`TaskIdInterceptor`/`CorsConfig` 均不接触响应体。

**结论**：后端代码层面 `classifying` 一定先于 `classified` 离开服务器，"同时到达"在后端发送逻辑上不成立 → 问题在别处，或另有机制。

### 2.2 发现后端问题一：Agent 步骤级静默（"步骤不实时"的直接原因）

走查 Agent 执行链路（`BaseAgent → ReActAgent → ToolCallAgent`，对比 simple_chat 的 `SimpleChatHandler`）后发现：

- `SimpleChatHandler` 用的是 `chatClient.stream()`，token 随生成随推，是实时的；
- 而 `ToolCallAgent.think()` 用的是**阻塞式 `.call()`** 调 DeepSeek。deepseek-v4-pro 默认开启 thinking 模式，单步推理要数十秒甚至分钟级，期间**零事件**；调用返回后 `reasoning`（一整块）+ `step` 事件同时爆发；
- `onFinish()` 里的 `generateMarkdownSummary()` 又是一次全量上下文的阻塞调用，结束前再贡献一段静默。

即：工作流/对比/sql_query 三个 Agent 流程的事件**天然只能成批到达**，这是"步骤对前端透明但不实时"的直接根因。

### 2.3 发现后端问题二：裸用 ForkJoinPool commonPool（并发放大器）

`IntentRouter.route()` 和 `BaseAgent.runStream()` 的 `CompletableFuture.runAsync(...)` **都没有传 executor**，默认使用 ForkJoinPool commonPool：

- commonPool 大小 = CPU 核数 - 1；
- Agent 的 step 循环是分钟级长任务，且绝大部分时间阻塞在同步 HTTP（LLM 调用）上——普通 socket 阻塞**不会触发** FJP 的补偿线程机制；
- 少量并发会话即可把 commonPool 占满，之后新请求的路由任务排队，连 `classifying` 事件都发不出去，前端看到一串事件同时到达。

这是"classifying/classified 同时到达"在后端**唯一成立**的机制，但它需要并发前提，无法解释单会话复现。（此前删掉的 `AsyncConfig` 是死代码，`runAsync` 从未用过它——commonPool 是一直以来的实际线程池。）

### 2.4 实锤：前端服务器 nginx 代理缓冲（无需并发即可复现）

查证 `docs/environment/nginx-env.md`，前端服务器 nginx 反代配置：

```nginx
location /api/ {
    proxy_pass http://xxx:8109/api/;
    ...
}
```

- **`proxy_buffering` 默认 `on`**：nginx 会把上游响应攒在缓冲区，攒满或响应结束才发给客户端。SSE 事件又小又稀疏，后端逐条 flush 的事件全被 nginx 攒住、成批吐给前端——"意图识别中/结果同时到达、步骤不实时"完全对上，且**单会话即可复现**；
- **`proxy_read_timeout` 默认 60s（未爆的定时炸弹）**：SSE 是长连接（后端 emitter 超时 300s），Agent 任务中工具执行、summary 生成都可能超过 60s 无事件，会被 nginx 中途断连；
- `proxy_http_version` 默认 1.0，无 chunked 编码，SSE 场景应升 1.1；
- `gzip` 排除嫌疑：`gzip_types` 不含 `text/event-stream`，SSE 响应不会被压缩。

## 3. 真实根因（三层）

| 层 | 根因 | 解释的现象 | 复现条件 |
|----|------|-----------|---------|
| 主因 | 前端 nginx `proxy_buffering` 默认开启，SSE 事件被代理攒批 | classifying/classified 同时到达、所有事件不实时 | 任何情况，单会话即可 |
| 后端 1 | `ToolCallAgent.think()` / summary 用阻塞 `.call()`，单步数十秒~分钟级零事件 | 工作流/对比步骤成批到达 | 任何情况（nginx 关缓冲后依然存在） |
| 后端 2 | `runAsync` 裸用 ForkJoinPool commonPool，长任务占满池 | 新会话连 classifying 都发不出，事件成批到达 | 需要并发会话 |

三层都要修：只改 nginx，步骤级静默还在；只改后端，nginx 缓冲还在。

## 4. 解决方案

### 4.1 后端修复（已实施并验证）

- **`ReasoningChatModel` 新增 `streamAggregated(Prompt, Consumer<String>)`**：复用既有 `mergeOptions`/`createRequest` 自建请求（保留 `reasoning_content` 回传，否则 tool call 轮次 DeepSeek 返回 400），`stream=true` 走流式；reasoning 增量实时回调；tool_call 分片按 `index` 合并（首片带 id/name，后续片拼接 arguments）；流结束后聚合成与 `call()` 完全同构的 `ChatResponse`，`think()`/`act()` 下游零改动。
- **`ToolCallAgent.think()` 改用流式聚合**：`reasoning` 事件从"每 step 一条整块"改为流式增量片段（与 simple_chat 语义一致）；`onFinish()` 在 summary 生成前补发 `thinking` 状态事件兜底最后一段静默。
- **新增 `ChatExecutorConfig.chatTaskExecutor`**（ThreadPoolTaskExecutor，core=8/max=32/queue=200）：`IntentRouter` 及三个 Agent Handler（SqlQuery/Workflow/Compare）注入使用，替代 commonPool；`BaseAgent` 保留 commonPool 默认值以兼容直接 new agent 的测试。
- **`ChatController` 增加防御性响应头**：`X-Accel-Buffering: no`（nginx 识别后对该响应自动关缓冲，即使 nginx 未改配置也生效）、`Cache-Control: no-cache`。

涉及文件：`ReasoningChatModel`、`ToolCallAgent`、`BaseAgent`、`DbSqlAgent`/`DbWorkflowAgent`/`DbCompareAgent`（构造器透传）、`SqlQueryHandler`/`WorkflowHandler`/`CompareHandler`、`IntentRouter`、`ChatController`、新增 `ChatExecutorConfig`。

### 4.2 nginx 配置修正（文档已更新，**需登录服务器应用**）

`docs/environment/nginx-env.md` 的 `location /api/` 已补充：

```nginx
proxy_buffering off;        # SSE 必需：关闭代理缓冲
proxy_read_timeout 360s;    # SSE 必需：>= 后端 emitter 超时 300s，防长任务被断连
proxy_http_version 1.1;     # 推荐：替代默认 1.0
proxy_set_header Connection "";
```

**注意**：文档只是记录，需登录前端服务器改配置并 `nginx -t && systemctl reload nginx` 才生效。

### 4.3 前端协调点

Agent 流程的 `reasoning` 事件语义变为**流式增量片段**（`api-docs.yaml`、README 已同步更新），前端需按追加渲染。simple_chat 本就是追加语义，大概率可复用同一处理逻辑；若此前对 Agent 的 reasoning 按 step 整块替换渲染，需要调整。
