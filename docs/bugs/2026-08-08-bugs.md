# 总结回复泄漏 DSML 工具调用原文：根因分析与工具调用链路修复

日期：2026-08-08
涉及模块：`db-genius-agent`（`ToolCallAgent`、新增 `DsmlToolCallParser`）

## 1. 现象与日志证据

部署"总结步骤流式化"后，前端总结卡片出现模型内部标记原文：

```
＜｜｜DSML｜｜tool_calls＞
＜｜｜DSML｜｜invoke name="executeSql"＞
＜｜｜DSML｜｜parameter name="dbConfigId" string="false"＞1＜/｜｜DSML｜｜parameter＞
＜｜｜DSML｜｜parameter name="sql" string="true"＞SHOW TABLES＜/｜｜DSML｜｜parameter＞
＜/｜｜DSML｜｜invoke＞
＜/｜｜DSML｜｜tool_calls＞
```

（示例中的尖括号为全角书写，实际日志为 ASCII `< >`；`｜` 为全角竖线 U+FF5C。）

DSML 是 DeepSeek 内部的"文本形式工具调用"标记。它出现在给用户的总结里，说明模型在总结轮次没有正常输出 Markdown，而是试图用纯文本"继续调用工具"。

线上完整日志（task 90e6e21a）给出了关键证据链：

```
[DbSqlAgent] selected 1 tools: executeSql
SqlExecuteTool - Executing statement on db null: null          ← 工具被以空参数执行
act results: Tool executeSql result: "Error: Database config not found for ID null"
（约 3 秒后）
INSERT message role=assistant type=summary content=＜DSML invoke executeSql dbConfigId=1 sql=SHOW TABLES＞
```

即：**工具确实被调用了，但参数全为 null；真实参数躺在模型正文的 DSML 文本里没被解析。**

## 2. 根因链

1. **模型降级输出**：DeepSeek 在 thinking 模式 + 流式输出下，偶发把工具调用"降级"——
   结构化 `tool_calls` 仍然存在但 `arguments` 为空（有时连 tool_calls 都缺失），
   真实参数被模型写进 `content` 的 DSML 标记。
2. **框架忠实执行空参调用**：`ToolCallAgent.act()` 不做参数校验，直接把空参调用交给
   `ToolCallingManager` 执行，`SqlExecuteTool` 收到 `dbConfigId=null`，
   返回 `Error: Database config not found for ID null`。
3. **错误反馈是噪音**：这条错误对模型来说不可理解（它"以为"自己传了参数），
   模型的协议认知被扰乱，后续轮次放弃结构化协议，改用纯文本 DSML 重试工具调用。
4. **时机放大了伤害**：事故发生在最后一步（step = maxSteps）。工具错误产生后，
   模型只剩一次"不带 tools 的总结调用"。模型在总结轮看到历史里"任务没完成"的错误，
   于是用 DSML 文本"继续任务"——这段文本经 `summary` 事件推给前端并落库。

一句话：**DSML 泄漏是果，空参工具调用被执行、模型拿到不可理解的错误才是因。**

## 4. 本次方案（治本为主，兜底为辅）

### 4.1 DSML 反解析恢复（治本，主修复）

新增 `DsmlToolCallParser`：

- `parse(content)`：解析 DSML invoke 块为 `(name, argumentsJson)`。参数类型按 `string` 属性还原：
  `string="true"` 恒为字符串；`string="false"` 依次尝试 Long → Double → Boolean，失败回退字符串。
  正则统一用 `[｜|]` 兼容全/半角竖线，并兼容无 DSML 前缀的简化 `<invoke>` 写法。
- `strip(content)`：四层正则（完整块 → 孤立闭合标签 → 简化块 → 残缺片段）剥离 DSML，正常 Markdown 无损。
- `containsDsml(content)`：快速探测。

`ToolCallAgent.think()` 在拿到流式聚合响应后调用 `recoverDsmlToolCalls`：

- 结构化 tool_calls 存在但 arguments 空白 → 按顺序用 DSML 反解析结果**填补参数**；
- 完全没有结构化 tool_calls → **合成**新调用（id 为 `dsml-i`）；
- content 经 `strip` 净化后重建 AssistantMessage（保留 metadata，reasoning_content 回传不受影响），
  消息历史保持结构化协议干净——**不再向后续轮次暴露 DSML 文本**，切断"教坏模型"的强化环；
- 恢复触发时打 `warn` 日志，线上可统计命中率。

### 4.2 空参护栏（恢复失败的兜底）

`act()` 执行前校验每个 tool call 的 arguments（非空白且为合法 JSON 对象）。
仍有非法调用时**绝不执行空参调用**，而是手工把 assistant 输出与合成的
`ToolResponseMessage`（id 与 tool call 一致，满足协议配对）写入消息历史，
工具结果为可行动的重试指引：

```json
{"success":false,"error":"Tool arguments were empty or invalid. Re-emit the tool call with all required parameters."}
```

模型拿到的是能理解并纠正的反馈，而非 `config not found for ID null` 式噪音。

### 4.3 总结提示词硬约束（次要防御）

`SUMMARY_SYSTEM_PROMPT` 增加规则 6：总结轮没有工具，禁止输出任何工具调用标记，只输出 Markdown。

### 4.4 总结输出安全网（最后兜底，明确不是主修复）

`generateMarkdownSummary` 的聚合全文经 `DsmlToolCallParser.strip` 后再发终态 `summary` 事件/落库；
剥离后为空则走 `fallbackSummary`。打字机增量（`summary_delta`）可能仍会闪过原文，
但终态事件是前端渲染的权威内容，会整体覆盖增量。

## 5. "错误有没有传给模型？"

传了，但有两个问题：

1. **内容是噪音**：`Database config not found for ID null` 与模型自认传了参数的事实矛盾，
   无法引导模型纠正，反而诱发降级；
2. **时机太晚**：错误产生在最后一步之后，模型只剩一次不带 tools 的总结调用能看到它，
   没有重试机会，于是选择了用 DSML 文本"自己把工具调了"。

本方案从两端修复：恢复真实参数让错误根本不产生；产生时用可行动的指引替代噪音，并确保模型还有轮次去纠正。

## 6. 注意事项

1. **DSML 变体多**：全角/半角竖线混用、简化 `<invoke>` 写法、残缺未闭合片段都可能出现。
   解析正则必须用 `[｜|]` 并容忍属性缺失；strip 要分层剥离而不是单条正则。
2. **参数类型要看 `string` 属性**：`string="false"` 的 `1` 必须是 JSON 数字，
   否则 `executeSql(Long dbConfigId)` 反序列化仍会失败；`string="true"` 的 `42` 必须保持字符串。
3. **重建消息必须保留 metadata**：DeepSeek thinking 模式要求把上一轮 `reasoning_content` 回传，
   重建 AssistantMessage 时丢失 metadata 会导致后续请求 400。
4. **合成的 ToolResponseMessage 的 id 必须与 tool call 对应**，否则 OpenAI 兼容协议校验失败。
5. **多供应商差异**：该降级行为目前只在 DeepSeek（thinking+流式）观察到，
   但恢复/护栏逻辑是供应商无关的防御，对其他模型无副作用（不含 DSML 时零开销路径）。
6. **分层定位要清楚**：`think()` 恢复与 `act()` 护栏是主修复；提示词规则与 summary strip 只是纵深防御。
   若未来再现泄漏，先查恢复日志（`Recovered N DSML tool call(s)`）是否命中，再谈过滤。
7. **流式总结放大了可见性**：此前总结一次性到达不易察觉，打字机化后逐字暴露。
   前端协议已约定终态 `summary` 覆盖 `summary_delta`，兜底清洗因此可接受。
8. **验证方式**：DSML 为模型偶发行为，难以手工复现；以单测模拟三种形态
   （空参+DSML、纯 DSML、空参无 DSML）为主要回归手段，见
   `DsmlToolCallParserTest` 与 `ToolCallAgentTest`；线上以 warn 日志统计命中率。
